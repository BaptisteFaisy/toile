Limits

This page is the inverse of the other ones: it lists what the project has not proven. Every line below comes from a measurement, from a reading of the virtio-gpu standard, or from a source file in this repository. Where a result is missing, it is written as missing. Nothing here is a roadmap item or a promise.

The guest paints into the emulator: that part is measured. A full QNX desktop driven by the Screen path: that part is not finished. This page is the distance between the two.

Proven / Not proven

ProvenNot proven
The typed API is frozen: 28 public signatures in CONTRACT.md §10, plus the typed devctl of /dev/gpu0 (0x50–0x55). No 3D. The emulator has no virgl renderer, so the 3D command family is out of reach; only the 2D command family works.
The driver runs in a real QNX 8.0 guest: it enumerates 1af4/1050, negotiates the device and publishes /dev/gpu0. No host→guest readback in 2D. The virtio-gpu 2D command set has no TRANSFER_FROM_HOST_2D; the only host→guest transfer is the 3D one, which needs virgl. The driver announces the refusal instead of faking it.
The test pattern painted by the guest is visible in the emulator: 1280×800, six colour bars. The production path is not finished. The guest client maps the framebuffer through the physical address; the real Screen path would go through the resmgr mmap callout, which is only partially validated.
The FNV-1a hash published by the guest equals the hash recomputed from the emulator's own screenshot. The live guest is a demo. An unrelated process on the workstation kills it every 1–2 minutes; systemd restarts it within 10 s, so the showcase works but has holes.
The virtio-input keyboard path: a real key reaches the guest, updates the shared animation state, and the painters follow. The showcase is slower than the guest. It captures the emulator screen about 7 times per second (the QEMU monitor screendump is the bottleneck); the guest paints at 30 im/s.
The portable core is deterministic: the same sequence gives the same state hash, byte for byte, and the C and Python twins agree. One shared framebuffer. Three clients own three bands, each presents its own rectangle. There is no compositor, no Z-order, no damage tracking, no per-client isolation.
CI builds the core and runs the unit tests, the differential and the guards. The E-series of trials is not in CI. It runs on a developer workstation with the QNX SDP; CI builds and unit-tests the core only.

What is not proven, item by item

No 3D

The emulator's virtio-gpu device is started without virgl. Without that renderer the device answers nothing to the 3D command family, so Toile implements and exercises the 2D family only: resources, backing, scanouts, flush, cursor. Nothing in this repository claims a 3D path, and nothing has been measured on one.

No host→guest readback in 2D

The virtio-gpu 2D command set contains one transfer, TRANSFER_TO_HOST_2D (0x0105), and it is guest→host. There is no TRANSFER_FROM_HOST_2D: the host→guest copy belongs to TRANSFER_FROM_HOST (0x0206), in the 3D family, and it needs virgl. When a client asks for it, the device answers 0x1200 (ERR_UNSPEC) and the driver reports the refusal explicitly. No fallback path fabricates a readback.

The Screen display driver path is not finished

What runs today is a client that maps the framebuffer through its physical address (MAP_PHYS) and paints into it, then asks the driver to present a rectangle. The production path for a QNX desktop is different: the display driver would take the framebuffer from the resource manager through the mmap callout, so that a client cannot write anywhere in the picture. That callout is only partially validated; the display-driver skeleton compiles and links against the real Screen interface, but its integration is not tested.

The live guest is a demo

The guest shown on the live page runs on a developer workstation. An unrelated process there kills the virtual machine every one or two minutes; systemd restarts it within about 10 s. The showcase therefore works, with holes: for a few seconds the page has no screen to show. It is a demonstration environment, not a service.

The showcase samples the screen, the guest paints it

The web showcase reads the emulator screen through the QEMU monitor (screendump), which gives about 7 captures per second. The guest paints at 30 images per second. What the page shows is therefore a sampled, decimated view of the animation, not the animation itself. The bottleneck is the monitor command, not the driver.

One framebuffer, three clients, no compositor

The guest clients paint one shared framebuffer. Three clients own three bands, and each one presents its own rectangle. There is no compositor, no Z-order between clients, no damage tracking, and no isolation: a client that mapped the framebuffer can write outside its band. The bands are a convention between cooperating clients, not an enforced boundary.

The trials are not automated

The E-series of trials needs the QNX SDP and QEMU, so it runs on a developer workstation with qcc and mkifs. CI builds and unit-tests the portable core only: the C core, the Python twin, the differential and the guards. A green CI run therefore says nothing about the guest driver, about QEMU, or about the trials.

What IS proven

The typed API is frozen

28 public signatures are frozen in CONTRACT.md §10 and mirrored in core/include/toile/ and host/toile/. On the guest side, /dev/gpu0 exposes a typed devctl API: INFO, FB, PRESENT, MIRE, ANIM_GET, ANIM_SET. The CI guard .github/checks/api-frozen.py fails the build if one of them disappears.

The driver runs in a real QNX 8.0 guest

Under QEMU with -device virtio-gpu-pci, the guest driver finds 1af4/1050 on the PCI bus, gets an answer to GET_DISPLAY_INFO (scanout 0, 1280×800), gets RESOURCE_CREATE_2D with backing and SET_SCANOUT accepted, and publishes /dev/gpu0. An ordinary client opens it, queries it and paints.

The guest-painted pattern is visible in the emulator

The test pattern is painted inside the guest, not injected from the host. The emulator window shows it: 1280×800, the scanout mode, six solid colour bars. The capture is made headless, through VNC and the monitor screendump.

The hash of the picture matches, on both sides

The guest computes the FNV-1a hash of the framebuffer it painted, publishes it on the serial console and holds the frame for 2.5 s (ANIM_HOLD_MS in guest/common/toile_anim_main.c). The host recomputes the hash from the pixels QEMU actually rendered and compares. The two hashes are equal, which shows that the bytes the guest painted are the bytes the emulator displays. One command: qemu/verify-hash.sh.

The keyboard reaches the painters

The chain is complete and exercised: a key sent to the QEMU monitor arrives through virtio-input, the guest driver reads it from the event queue, writes the shared animation state through devctl, and the painters read that state. Palette, speed and pause change on the screen because a key was pressed.

How to reproduce

  1. The core, anywhere, without QNX, QEMU or GPU: make build && make test — C unit tests, Python unit tests, the C↔Python differential on the fixtures, then the size and frozen-API guards.
  2. The guest driver in a real guest: qemu/probe-driver.sh — builds the image, starts the VM, waits for the proof (device found, /dev/gpu0 published), stops the VM.
  3. The painted pattern in the emulator: qemu/run-demo.sh — boots the guest, paints the pattern from inside it, captures the screen and reports the verdict.
  4. The hash proof, in one command: qemu/verify-hash.sh — the guest publishes its FNV-1a and holds the frame; the host recomputes the hash from the screenshot and compares.
  5. The persistent guest behind the showcase: qemu/toile-vitrine.sh — the same VM, left running under systemd, with the serial log and the monitor socket the showcase reads.
  6. The readback refusal: ask a client for TRANSFER_FROM_HOST (0x0206) and read the serial log: the device answers 0x1200 (ERR_UNSPEC), and the driver says so.

The scripts of points 2 to 5 need the QNX SDP (qcc, mkifs) and QEMU. Point 1 needs neither, and is the only one CI runs.
